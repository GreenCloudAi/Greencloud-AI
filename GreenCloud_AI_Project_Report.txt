1. PROBLEM STATEMENT AND OBJECTIVES
==========================================================================================

1.1 Problem Statement
---------------------
Public cloud platforms make it easy to start computing resources and easy to forget them.
Engineers launch virtual machines, storage volumes, static IP addresses, and other
resources for testing or temporary workloads, and those resources keep billing after they
are no longer needed. Instances are also commonly over-provisioned "to be safe", so a
machine that peaks at 15-20% CPU continues to be billed at the price of a much larger size.

Cost information arrives late. Cloud bills typically become visible 24-48 hours after
usage, which means waste is often discovered only at month-end. Native provider tools are
scoped to one provider and mostly advisory: they show dashboards and recommendations but do
not close the loop with evidence, approval, and safe execution.

Cloud usage also has an environmental cost. Every running server draws electricity, and the
carbon emitted per kilowatt-hour depends heavily on the region's electricity grid. The same
workload can produce many times more emissions in a coal-heavy region than in a
hydro-powered one. Carbon reports differ between providers in scope, granularity, and
method, and are rarely connected to the specific resources a team can change.

During development, the team also observed a practical visibility problem: when an AWS
account was scanned only in the default region (us-east-1), an EC2 instance actively
running in ap-south-1 (Mumbai) was not reported correctly. Incomplete visibility leads to
wrong conclusions, which is worse than having no optimization tool at all.

Therefore, the problem addressed by GreenCloud AI is the need for a single platform that
(a) connects securely to a cloud account with read-only access, (b) discovers resources in
every enabled region, (c) reconciles cost with the provider's billing data, (d) estimates
operational and embodied carbon per resource, (e) detects idle and oversized resources,
and (f) presents ranked, evidence-backed recommendations that people can review, approve,
and act on with an audit trail.

1.2 Objectives
--------------
  * Build a secure onboarding flow through which a user can connect an AWS account using a
    cross-account IAM role (STS AssumeRole with External ID) or encrypted access keys,
    without the platform holding shared static credentials.
  * Discover EC2 instances, EBS volumes, and Elastic IP addresses across all enabled AWS
    regions, and record each resource with its region, lifecycle state, and monthly cost.
  * Collect CPU utilization telemetry from Amazon CloudWatch for running instances.
  * Reconcile billed spend with AWS Cost Explorer so the dashboard reflects actual charges.
  * Estimate operational and embodied carbon emissions per resource using region-specific
    grid carbon intensity, and compute a Software Carbon Intensity (SCI) score.
  * Generate rule-based recommendations for idle instances, unattached volumes, unused
    Elastic IPs, and rightsizing to smaller or Graviton (Arm64) machines, each with risk
    score, confidence, savings estimate, and calculation evidence.
  * Forecast cost and carbon 30 days ahead with confidence bounds, and detect spending
    anomalies statistically.
  * Provide a human-in-the-loop approval workflow, ticket/PR blueprints, and an audit log
    of every connection, sync, and approval action.
  * Provide a dashboard for cost, sustainability, optimization, and executive reporting.

1.3 Scope of the Project
------------------------
The project scope is a college mini-project that demonstrates a working FinOps + GreenOps
pipeline for Amazon Web Services (AWS). It covers secure account connection, multi-region
resource discovery, CloudWatch telemetry, Cost Explorer reconciliation, carbon estimation,
recommendation generation, forecasting and anomaly detection, an approval workflow, audit
logging, and a web dashboard. Azure, Google Cloud, Kubernetes cost allocation, live grid
carbon APIs, enterprise authentication, and automatic infrastructure changes are described
as future scope. The project does not claim that its carbon figures are audited emissions
or that its heuristics identify the optimal configuration for every workload.

1.4 Expected Outcome
--------------------
The intended outcome is a prototype in which a user connects an AWS account through the
onboarding wizard, triggers a telemetry sync, and sees on the dashboard: billed spend
reconciled with Cost Explorer, a multi-region resource inventory, per-resource carbon
estimates, ranked recommendations with evidence, cost/carbon forecasts with anomaly flags,
and an exportable executive report. Approving or dismissing a recommendation is recorded in
the audit history.

2. ABSTRACT
==========================================================================================

Cloud computing costs and cloud-related carbon emissions both grow when resources are left
idle or over-provisioned, yet most teams discover waste only after the bill arrives.
GreenCloud AI addresses this problem with a FinOps and GreenOps platform that connects to
an AWS account using read-only access, discovers resources across all enabled regions, and
turns raw billing and telemetry data into evidence-backed optimization recommendations. The
system is built with Next.js 14, React 18, and TypeScript for the frontend and API routes,
Prisma ORM with SQLite for persistence, and the AWS SDK v3 (STS, EC2, CloudWatch, Cost
Explorer) for cloud integration. Credentials provided by users are encrypted at rest with
AES-256-GCM. A carbon engine estimates operational emissions from vCPU power draw and
region-specific grid intensity (gCO2e/kWh), adds an embodied-hardware share, and computes a
Green Software Foundation SCI score. A rule-based recommendation engine flags idle
instances (average CPU below 5%), unattached EBS volumes, unassociated Elastic IPs, and
rightsizing opportunities (peak CPU below 40%), mapping each instance to a smaller x86 or
AWS Graviton target from a built-in machine catalogue, with a risk score, confidence value,
and calculation evidence. A forecasting engine applies damped Holt's linear trend smoothing
to project cost and carbon for 30 days with 95% confidence bounds, and detects anomalies
using rolling Z-scores (>= 2.5 sigma) and the interquartile range. Recommendations follow a
human-in-the-loop approval workflow, and every action is written to an audit log. The
dashboard provides Overview, Cost & Usage, Sustainability, Optimization, and Executive
Report sections. The project is partially implemented: the AWS pipeline, forecasting,
recommendations, and dashboard are working, while multi-cloud connectors, live grid-carbon
APIs, enterprise authentication, and real infrastructure execution remain future work.

Keywords: FinOps, GreenOps, Cloud Cost Optimization, Carbon Accounting, Software Carbon
Intensity, AWS, Rightsizing, Time-Series Forecasting, Anomaly Detection.

3. INTRODUCTION
==========================================================================================

3.1 Background
--------------
Cloud computing lets organizations rent compute, storage, and networking on demand instead
of buying hardware. Billing is usage-based: each running instance, attached volume, and
reserved IP address accrues charges by the hour or by the gigabyte. This flexibility is
valuable, but it also means that every forgotten or oversized resource keeps costing money.

FinOps is the operating practice of making cloud spending visible, attributable, and
optimizable. The FinOps Foundation framework groups this work into domains such as
understanding usage and cost, quantifying business value, optimizing usage and cost, and
managing the FinOps practice, with capabilities including data ingestion, allocation,
forecasting, anomaly management, and automation.

GreenOps extends FinOps with carbon measurement and reduction. The Green Software
Foundation's Software Carbon Intensity (SCI) specification states that software emissions
come from the energy consumed by hardware and from the emissions associated with
manufacturing that hardware, and recommends energy efficiency, hardware efficiency, and
carbon-aware actions.

3.2 Need for a Combined FinOps + GreenOps Platform
--------------------------------------------------
Cost and carbon are closely linked. An idle instance wastes money and electricity at the
same time; moving a workload to a more efficient processor (for example, AWS Graviton Arm64)
or to a cleaner region can reduce both. Yet cost tools and carbon tools are typically
separate, and carbon reports are rarely tied to specific resources that an engineer can
change. GreenCloud AI is designed as a decision system rather than only a dashboard. It
aims to answer:

  1. What are we spending, and on what?
  2. Which resources are idle, oversized, or carbon-intensive?
  3. What will spending and emissions look like over the next month?
  4. Which action saves the most money and gCO2e with the lowest risk?
  5. What evidence supports each recommendation, and who approved it?

3.3 GreenCloud AI Overview
--------------------------
GreenCloud AI is a web application in which a user connects a cloud account, triggers a
sync, and reviews results on a dashboard. Internally, an ingestion pipeline validates the
account, assumes a read-only role, scans all enabled regions for compute, storage, and
network resources, fetches CloudWatch CPU telemetry, reconciles cost with Cost Explorer,
calculates carbon emissions, generates recommendations, and records every step in an audit
log. The dashboard presents the results in cost, sustainability, optimization, and
executive-report views.

3.4 Challenges in Existing Workflows
------------------------------------
  * Late cost feedback: bills appear after 24-48 hours, so waste is discovered at month-end.
  * Incomplete visibility: scanning one default region can miss resources in other regions.
  * Advisory-only tools: native advisors suggest changes but do not provide an approval,
    evidence, and audit workflow.
  * Provider-specific carbon data: carbon reports differ in scope, granularity, and method,
    and are not linked to individual resources.
  * Credential risk: sharing static access keys with a third-party tool, or storing one
    shared role in a hosted environment, exposes administrative access.
  * Trust: recommendations without visible calculations are hard to approve.

3.5 Motivation
--------------
The motivation behind GreenCloud AI is to make cloud waste visible quickly and to make
each recommendation explainable. The team adopted a "zero fake data" rule during
development: placeholder accounts, static savings banners, and fabricated figures were
removed from the product, and the dashboard spend was reconciled against the AWS Billing
Console of a live test account (the dashboard matched the console's month-to-date spend to
within the live accrual difference). The goal is a tool whose numbers can be traced back to
the cloud provider's own data.

3.7 Read-Only, Multi-Tenant Cloud Connection
--------------------------------------------
GreenCloud AI is designed so that the standard connector needs no write permission. The
preferred method is a cross-account IAM role: the user creates a role in their AWS account
that trusts GreenCloud AI, and the platform calls STS AssumeRole with an External ID. The
External ID protects against the "confused deputy" problem, where a third party tricks a
service into acting on the wrong account. As an alternative, a user may supply access
keys; these are encrypted with AES-256-GCM before storage, with a random IV and an
authentication tag, so tampering is detected on decryption. Each cloud account belongs to a
tenant, and database access goes through a TenantIsolatedDb abstraction so that one
tenant's data is not returned to another.

3.8 Multi-Region Resource Discovery
-----------------------------------
When GREENCLOUD_SCAN_REGIONS is set to "all" (the default), the AWS connector calls EC2
DescribeRegions to find every region enabled for the account, falling back to a list of 17
standard regions if that call is unavailable. In each region it runs DescribeInstances,
DescribeVolumes (to find unattached EBS volumes), and DescribeAddresses (to find
unassociated Elastic IPs). Every resource is stored with its region, lifecycle state,
instance type or size, estimated monthly cost, tags, and first/last-seen timestamps.

3.9 Carbon Estimation
---------------------
The carbon engine follows the structure of the SCI specification:

    SCI = (O + M) / R

where O is operational emissions (energy x grid carbon intensity), M is the embodied
emissions share of the hardware, and R is the functional unit.

For an EC2 instance over a period of hours:

    Power (W)        = vCPUs x (15 + (45 - 15) x avgCPU%)
    Energy (kWh)     = Power / 1000 x hours
    Operational gCO2e = Energy x grid intensity of the region (gCO2e/kWh)
    Embodied gCO2e   = (1,200,000 gCO2e / 35,040 h) x (vCPUs / 64) x hours

The idle (15 W) and peak (45 W) per-vCPU figures follow Cloud Carbon Footprint style
coefficients; the embodied model assumes a 64-vCPU host with 1.2 tCO2e manufacturing
emissions and a 4-year life. For EBS volumes, energy is estimated at 0.0005 Wh per GB-hour
and embodied emissions at 0.0002 gCO2e per GB-hour. Regional grid intensities are a static
baseline table, for example:

    Region           Grid intensity (gCO2e/kWh)   Notes
    --------------   --------------------------   -------------------------------
    eu-north-1       45                           Stockholm - hydro and nuclear
    us-west-2        80                           Oregon - high hydro share
    us-west-1        210                          N. California
    eu-west-1        310                          Ireland
    us-east-1        420                          Virginia
    ap-southeast-1   480                          Singapore
    ap-south-1       680                          Mumbai - coal-heavy grid
    default          350                          Used for unlisted regions

These are average, not hourly marginal, intensities, and they are estimates rather than
provider-reported emissions. Each emission record stores its method and a confidence
value so estimates can be distinguished from measured data.

3.10 Recommendation Logic
-------------------------
The recommendation engine evaluates each discovered resource against configurable rules:

    Rule                      Condition                                 Category       Risk
    ------------------------  ----------------------------------------  -------------  -----
    Unattached EBS volume     Volume state "available" (not attached)   idle_cleanup   0.10
    Unassociated Elastic IP   Address not associated with an instance   idle_cleanup   0.05
    Stopped instance review   Instance stopped; attached EBS/EIP still  idle_cleanup   0.15
                              billed (review, create AMI, terminate)
    Idle running instance     Average CPU < 5% over lookback window     idle_cleanup   0.35
    Rightsizing               Avg CPU >= 5% and peak CPU < 40%          rightsizing    0.20

Confidence is 0.9 when at least 7 days of CloudWatch data are available and 0.7 otherwise.
Each recommendation stores a JSON "evidence" record containing the calculation (instance
type, monthly cost, average and peak CPU, lookback days) and a plain-language reason.

For rightsizing, a machine catalogue of about 40 EC2 instance types (t2, t3, t4g, m5, m7g,
c5, c7g, r5 families) with vCPU, memory, architecture, and on-demand monthly price is used
to choose a target. For each current type, the engine picks an AWS Graviton (Arm64) target
and a same-family x86 alternative based on peak CPU (for example, an m5.xlarge with peak CPU
below 25% maps to t4g.medium, with t3.medium as the x86 alternative). It then computes
monthly and annual savings, a projected peak CPU on the target, and a safety headroom of at
least 25%. It also produces the matching AWS CLI command and a Terraform snippet.

4. LITERATURE REVIEW
==========================================================================================

The literature review focuses on research and standards related to energy-efficient cloud
resource management, workload forecasting, carbon-aware computing, cost optimization, and
grounded AI assistants. These works provide conceptual foundations for GreenCloud AI. They
do not imply that the prototype implements the same algorithms.

4.1 Review of Related Research
------------------------------

[1] Beloglazov & Buyya (2010) - Energy Efficient Resource Management in Virtualized Cloud
    Data Centers
    Approach   : Dynamic VM consolidation and live migration heuristics, evaluated in
                 simulation.
    Strengths  : Shows that consolidation can save substantial energy while preserving QoS.
    Limitations: Simulation-based; live-migration overhead in real systems.

[2] Verma et al. (2015) - Large-scale cluster management at Google with Borg
    Approach   : Production cluster manager using admission control, bin-packing,
                 overcommitment, and isolation.
    Strengths  : Demonstrates high utilization in production at very large scale.
    Limitations: Google-internal system; not directly transferable to customer accounts.

[3] Rzadca et al. (2020) - Autopilot: Workload Autoscaling at Google
    Approach   : Automatic horizontal and vertical scaling using sliding windows and an ML
                 recommender.
    Strengths  : Autopiloted jobs had 23% slack versus 46% for manually managed jobs, and
                 severe out-of-memory impact was reduced about 10x.
    Limitations: Internal data; adoption required organizational effort.

[4] Moreno-Vozmediano et al. (2019) - Efficient Resource Provisioning for Elastic Cloud
    Services Based on Machine Learning Techniques
    Approach   : SVM time-series forecasting combined with queuing theory for predictive
                 autoscaling.
    Strengths  : Better forecasting accuracy than simple moving-average baselines.
    Limitations: Evaluated on a single service pattern; not multi-cloud.

[5] Kumar & Singh (2020) - Performance Assessment of Time Series Forecasting Models for
    Cloud Datacenter Workload Prediction
    Approach   : Comparison of six forecasting approaches on real server traces.
    Strengths  : Auto-ARIMA achieved the best statistical rank, showing that classical
                 statistical baselines remain competitive.
    Limitations: Does not cover modern container workloads.

[6] Rossi et al. (2025) - Forecasting Workload in Cloud Computing: Uncertainty-Aware
    Predictions and Transfer Learning
    Approach   : Bayesian deep learning and transfer learning on Google and Alibaba traces.
    Strengths  : Shows the value of prediction intervals for service-level decisions.
    Limitations: More complex and compute-intensive than statistical methods.

[7] Goiri et al. (2011) - GreenSlot
    Approach   : Scheduling batch jobs to match solar energy availability within deadlines.
    Strengths  : Increased green energy use by up to 117% and reduced energy cost by up to
                 39% compared with a conventional scheduler.
    Limitations: Solar-powered datacenter setting; not a generic public cloud.

[8] Radovanovic et al. (2021) - Carbon-Aware Computing for Datacenters
    Approach   : Day-ahead carbon-intensity forecasts and virtual capacity curves to shift
                 flexible workloads to lower-carbon hours.
    Strengths  : Demonstrates temporal carbon shifting in a production fleet.
    Limitations: Google-specific; preprint.

[9] Hanafy et al. (2023) - CarbonScaler
    Approach   : Carbon-aware elastic scaling of batch workloads on Kubernetes.
    Strengths  : 51% carbon savings versus a carbon-agnostic baseline.
    Limitations: Applies only to elastic or batch workloads.

[10] Chen, Lei & Moinzadeh (2024) - Cost Optimization in Cloud Computing: Capacity
     Reservation for Intermittent Random Demand Surges
    Approach   : Stochastic operations model for reserved-capacity decisions.
    Strengths  : Shows commitment planning is an optimization under uncertainty.
    Limitations: Analytical assumptions; not provider-specific.

[11] Yao et al. (2023) - ReAct; Lewis et al. (2020) - Retrieval-Augmented Generation
    Approach   : LLMs that combine reasoning with tool actions (ReAct) and ground answers in
                 retrieved documents (RAG).
    Strengths  : Basis for an evidence-grounded cloud assistant.
    Limitations: Hallucination and tool-safety risks; require approval gates and audit logs.

4.2 Standards and Industry Tools
--------------------------------
  * Green Software Foundation SCI: defines SCI = (O + M) per R, where O = E x I and
    embodied emissions are allocated by time share and resource share.
  * Cloud Carbon Footprint (open source): multi-cloud estimator using billing data, power
    coefficients, PUE, and grid factors; uses point estimates without confidence intervals.
  * Google Cloud Carbon Footprint: machine-level energy allocation with location-based
    (hourly) and market-based reporting; customer reports are not third-party assured.
  * FinOps Framework and FOCUS: an operating framework and a normalized cost and usage
    data specification across vendors.
  * Native advisors (AWS Compute Optimizer, AWS Trusted Advisor, Azure Advisor, Google
    Recommender): provider-specific recommendations, mostly advisory.
  * Commercial platforms (CloudHealth, CloudZero, Kubecost/OpenCost, CAST AI, Harness,
    Flexera, IBM Turbonomic): strong cost visibility and, in some cases, automation; public
    evidence of resource-level SCI or combined cost + carbon ranking was not found.

4.3 Key Findings from the Literature
------------------------------------
  * Idle resources and over-provisioning are major sources of both cost and energy waste;
    consolidation and rightsizing reduce both.
  * Forecasts should include confidence intervals, because a wrong downsizing decision can
    break service levels. Statistical baselines remain strong for cloud workloads.
  * Carbon depends on where and when a workload runs; region and time choices matter.
  * Automation should be conservative: thresholds, approvals, change windows, rollback, and
    audit logs are needed before actions are executed.
  * Explainability is a product requirement; recommendations must carry their evidence.

4.4 Research Gap and Project Positioning
----------------------------------------
Public evidence shows gaps in (1) ranking actions by cost savings, carbon impact, and risk
together, (2) resource-level SCI reporting, (3) transparent carbon data-quality scoring, and
(4) evidence-backed, approval-gated remediation. GreenCloud AI is positioned as a compact
application-level prototype that combines read-only multi-region discovery, cost
reconciliation, resource-level carbon estimation, evidence-backed recommendations, and a
human-in-the-loop workflow. Its contribution is integration and transparency at the
mini-project scale, not a new state-of-the-art optimization algorithm.

5. PROPOSED METHODOLOGY
==========================================================================================

5.1 System Overview
-------------------
The methodology follows a sequential pipeline. A user connects an account through the
onboarding wizard. On sync, the backend validates the account, assumes the read-only role,
discovers resources in all enabled regions, collects telemetry, reconciles cost, estimates
carbon, generates recommendations, and writes audit entries. The dashboard API aggregates
the stored data, runs the forecasting engine, and returns KPIs, inventory, carbon,
forecast, anomaly, and recommendation data to the frontend.

5.2 Overall Workflow
--------------------
  1. Admin connects an AWS account (IAM role ARN + External ID, or encrypted access keys).
  2. The system validates the connection with STS and records the account as active.
  3. User triggers "Sync Telemetry" (POST /api/cloud-accounts/{id}/sync).
  4. The connector discovers enabled regions and scans EC2, EBS, and Elastic IPs.
  5. CloudWatch GetMetricData returns CPU utilization for each running instance over the
     configured lookback window (default 7 days, daily period).
  6. Cost Explorer GetCostAndUsage reconciles billed spend by service.
  7. The carbon engine computes energy, operational, and embodied emissions per resource.
  8. The recommendation engine applies rules and stores recommendations with evidence.
  9. Sync freshness, any sync error, and audit entries are stored.
 10. The dashboard API runs forecasting and anomaly detection and returns aggregated data.
 11. A user reviews a recommendation, approves or dismisses it, and the decision is logged.

5.5 Forecasting and Anomaly Detection Logic
-------------------------------------------
The forecasting engine uses Holt's linear trend method with Gardner-McKenzie trend damping:

    Level : L_t = alpha * Y_t + (1 - alpha) * (L_{t-1} + phi * T_{t-1})
    Trend : T_t = beta * (L_t - L_{t-1}) + (1 - beta) * phi * T_{t-1}

with default alpha = 0.35, beta = 0.15, and phi = 0.80. It projects daily cost ($/day) and
operational carbon (gCO2e/day) for 30 days. The 95% confidence band widens with the
forecast horizon h:

    margin = 1.96 x residual standard error x sqrt(min(h, 9))

Anomalies are flagged when a day's value exceeds the rolling mean by at least 2.5 standard
deviations (Z-score) or exceeds Q3 + 1.5 x IQR. Each anomaly includes a root-cause hint and
a suggested action. The engine also produces a calendar-aware month-end run-rate projection
and a budget-risk level.

5.6 Safety and Approval Strategy
--------------------------------
  * The standard connector uses read-only permissions; no write permission is required.
  * Every recommendation carries a risk score (0.0-1.0), a confidence value, and evidence.
  * Recommendations move through states: active -> approved / dismissed (-> executed).
  * Approvals are stored with approver, decision, comment, and timestamp.
  * Rightsizing targets keep at least 25% CPU headroom on the projected target machine.
  * AWS API calls use bounded retries (default 3) with exponential backoff (base 1000 ms).
  * Sync failures are recorded in the account's syncError field rather than hidden.

5.7 Data Management
-------------------
Prisma ORM with SQLite (prisma/dev.db) stores eight entities: Tenant, CloudAccount,
CloudResource, CostLineItem, CarbonEmission, Recommendation, Approval, and AuditLog.
Credentials are stored only in encrypted form. Telemetry and evidence are stored as JSON
strings. Cascading deletes keep child records consistent when an account or tenant is
removed. A cleanup endpoint removes duplicate test accounts created during repeated
onboarding.

5.8 Security Considerations
---------------------------
  * Prefer cross-account IAM roles with External ID over static access keys.
  * Encrypt any user-provided keys with AES-256-GCM; derive the key from ENCRYPTION_SECRET
    held in server-side environment variables.
  * Never expose credentials to frontend code or commit .env.local to Git.
  * Isolate tenant data through the TenantIsolatedDb abstraction.
  * Keep short STS session durations (default 900 seconds).
  * Record every connect, sync, approval, and optimization action in the audit log.

8. CONCLUSION AND FUTURE SCOPE
==========================================================================================

8.1 Conclusion
--------------
GreenCloud AI addresses a practical problem in cloud operations: waste in cost and carbon
that stays invisible until the bill arrives. The prototype connects securely to an AWS
account with read-only access, discovers resources across all enabled regions, reconciles
spend with Cost Explorer, estimates operational and embodied carbon per resource, and
generates evidence-backed recommendations with risk and confidence scores. A forecasting
engine projects cost and carbon with confidence bounds and flags anomalies, and every
decision is recorded through an approval workflow and audit log.

The literature shows that rightsizing, consolidation, forecasting with uncertainty, and
carbon-aware placement are effective ways to reduce both cost and emissions, and that
automation must be conservative and explainable. GreenCloud AI applies these ideas with
transparent rules and formulas rather than a trained model.

The project is partially implemented. The AWS pipeline, carbon and recommendation engines,
forecasting, dashboard, approvals, and audit history are in place, and the forecasting
tests pass. Multi-cloud connectors, live grid-carbon data, enterprise authentication,
scheduled syncs, real infrastructure execution with rollback, and full measured evaluation
remain to be completed.

8.2 Limitations
---------------
  * Only AWS is supported; Azure and GCP connectors are not yet implemented.
  * Grid carbon intensities are static regional averages, not live hourly marginal values.
  * The vCPU estimate in the carbon engine is coarse (derived from the instance-type name),
    so energy figures are approximate.
  * Recommendations use CPU only; memory, disk, and network are not yet considered.
  * Machine-catalogue prices are fixed on-demand rates and do not reflect discounts,
    Savings Plans, or price changes.
  * In-app fast optimization updates GreenCloud's records; it does not change AWS resources.
  * There is no user login or role-based access control yet; a default tenant is used.
  * Syncs are triggered manually; there are no scheduled background jobs.
  * SQLite suits a prototype but not a high-concurrency production service.

8.3 Future Scope
----------------
  * Azure connector (Resource Graph, Monitor, Cost Management, Advisor) and GCP connector
    (Compute Engine, Cloud Monitoring, BigQuery billing export, Recommender).
  * Live grid carbon intensity from Electricity Maps or WattTime, with location-based and
    market-based reporting.
  * Kubernetes cost and carbon allocation through OpenCost and Prometheus.
  * Terraform/OpenTofu pull-request generation through a GitHub App, and two-way Jira sync.
  * Execution guardrails: pre-flight health checks, snapshots, and an automatic rollback
    watcher after changes.
  * Enterprise authentication (NextAuth/Clerk, SSO) with roles: Admin, FinOps Lead,
    GreenOps Lead, Team Lead/Viewer.
  * Scheduled ingestion every 6 hours (Vercel Cron or Inngest) and migration to PostgreSQL.
  * Memory- and network-aware rightsizing, commitment (RI/Savings Plan) simulation, and
    carbon-aware scheduling.
  * An evidence-grounded AI assistant (RAG + ReAct) to explain recommendations.

8.4 Final Remark
----------------
GreenCloud AI provides a foundation for treating cloud cost and cloud carbon as one
optimization problem. Its value lies in combining secure discovery, transparent
calculations, and human-approved actions in one workflow. Further implementation and
measured evaluation will determine how much cost and carbon it can save in practice.
